## D-018 | 2026-10-06 | 1.8.1 긴급 수정: 전환 입력의 프레임 속도를 지우지 않는 방식으로 xfade 실패 해결
- **상태**: 채택
- **맥락**: 1.8.0에서 가운데 맞춤 전환을 빠른 xfade로 바꾼 뒤 검정·흰색 전환 전부, 위 트랙(V2) 디졸브·와이프·검정·흰색 전환의 내보내기가 'Conversion failed'로 실패했다(60가지 중 21가지). 클립 입력 끝의 `setpts=PTS-STARTPTS`가 프레임 속도 정보를 1/0으로 지워 xfade가 입력을 거부했다.
- **결정**: `_build_segment` 클립 입력 끝의 `setpts`를 빼고(앞의 fps가 이미 0부터 이어 붙인 시각), 전환 출력은 `exact()`로 마지막 장면을 채워 정확히 n 프레임으로 자른다.
- **이유**: 프레임 속도 정보가 처음부터 유지되면 xfade·blend가 그대로 동작하고, 구간마다 프레임 수가 정확해야 뒤 구간의 화면·소리 싱크가 밀리지 않는다.
- **버린 대안**: 전환 입력마다 `fps=` 를 덧붙이기 — 입력이 끝날 때 마지막 프레임을 버려 구간이 1프레임 짧아지고(뒤쪽 화면이 1프레임 밀림) 실행에 따라 결과가 달랐다.
- **영향/제약**: `tests/test_export_trans.py`가 실제 ffmpeg로 전환 8종을 내보내 길이·프레임 수(240)를 확인한다. 같은 수정에서 편집본 복제·이름 바꾸기는 `auto: "user"`로 표시해 '가편집 다시 만들기'가 지우지 않게 했다.

> D-001~D-017은 문서 체계를 도입하면서(2026-10-06) 그때까지의 결정을 한꺼번에 옮겨 적은 것이다. 날짜는 모두 기록한 날이다.

## D-013 | 2026-10-06 | 실행기가 앱을 같은 프로세스에서 실행 (runpy)
- **상태**: 채택
- **맥락**: 모든 실행(바탕화면·시작 메뉴 아이콘, `시작하기 (Windows).bat`, 업데이트 후 재시작)이 `updater.py --launch`를 거치게 했다. 처음 설계처럼 실행기가 `app.py`를 별도 프로세스로 띄우면, 사용자가 켜진 창을 작업 표시줄에 고정할 때 `pythonw app.py`가 고정된다. 그러면 그 아이콘은 실행기를 건너뛴다.
- **결정**: `updater.run_app()`이 업데이트 확인 뒤 `runpy.run_path("app.py")`로 같은 프로세스에서 앱을 켠다.
- **이유**: 아이콘이 띄운 프로세스가 곧 앱 창이어야 Windows가 창을 그 아이콘과 묶는다. 그래야 고정한 아이콘도 업데이트 확인·되돌리기를 거친다.
- **버린 대안**: 실행기가 `pythonw app.py`를 분리 실행 — 작업 표시줄 고정이 실행기를 우회.
- **영향/제약**: 새 버전이 켜지다 Python 오류로 멈추면 `_start_failed`가 바로 되돌린 뒤 이전 버전을 새 프로세스로 켠다. `ensure_shortcut`은 예전에 고정한 작업 표시줄 아이콘(`User Pinned\TaskBar`)도 실행기 경로로 고친다. 실제 Windows 검증은 남아 있다 (`KNOWN_ISSUES.md` I-015).

## D-012 | 2026-10-06 | pip 설치는 requirements.txt가 바뀐 버전에서만
- **상태**: 채택
- **맥락**: 예전 업데이트는 매번 `pip install -r requirements.txt`를 돌렸다. 몇 분이 걸리고, 인터넷 상태에 따라 실패할 수 있다.
- **결정**: 설치된 requirements의 sha256을 앱 폴더의 `.req_hash`에 기억하고, 바뀐 버전에서만 pip을 돌린다. pip이 실패하면 업데이트를 취소하고 되돌린다.
- **이유**: 대부분의 업데이트는 파이썬·HTML 파일만 바뀐다. pip을 건너뛰면 업데이트가 빠르고 실패 지점도 줄어든다.
- **버린 대안**: 매번 pip — 느리고 실패 위험 / constraints.txt로 전체 버전 고정 — 범위가 커서 보류.
- **영향/제약**: requirements를 고치는 배포는 사용자 PC에서 pip이 돈다는 점을 알고 배포한다. 실패하면 `.req_hash`에 `failed`가 기록되어 다음 업데이트 때 다시 설치한다.

## D-011 | 2026-10-06 | 배포 zip을 배포 커밋에 고정 (배포마다 커밋 2개), GitHub 릴리스·태그를 쓰지 않음
- **상태**: 채택
- **맥락**: 업데이트는 main의 `manifest.json`을 보고 zip을 받는다. main 압축본(`main.zip`)을 받던 방식에서는 배포 뒤 main에 커밋이 더 쌓이면 zip 내용이 manifest의 버전·지문과 달라진다. 이 저장소에는 GitHub 릴리스·태그 권한이 없다.
- **결정**: `release.sh`가 커밋 1(버전 + 파일 지문을 적은 manifest)을 만들고, 커밋 2에서 manifest에 `zip=…/archive/<커밋1>.zip`과 `commit`을 더해 main에 푸시한다.
- **이유**: zip이 특정 커밋에 고정되어, 배포 뒤 main이 바뀌어도 받는 파일이 manifest와 정확히 일치한다. 릴리스·태그 권한 없이 GitHub의 커밋 압축본만으로 된다.
- **버린 대안**: GitHub 릴리스 자산 + 태그 — 권한 없음 (태그 push는 403) / `main.zip` (v1.2 무렵부터 쓰던 방식) — 배포 뒤 커밋과 섞임.
- **영향/제약**: `release.sh`는 `git add -A`를 하므로 커밋 안 한 작업이 있으면 깨끗한 클론에서 배포한다 (`KNOWN_ISSUES.md` I-016). 태그 push 실패는 무시한다 (I-010). v1.7.1 이하 PC는 zip 속 manifest를 그대로 가져가므로 커밋 1에도 `files`를 넣는다 (1.7.1 → 1.8.0 확인).

## D-010 | 2026-10-06 | 안전한 업데이트: 파일 지문 확인 + 자동 되돌리기
- **상태**: 채택
- **맥락**: v1.7.1까지는 zip을 받아 앱 폴더에 바로 덮어썼다. 받다 끊기거나 새 버전이 안 열리면 반쯤 바뀐 앱이 남고, 비전문가 사용자는 복구할 수 없다.
- **결정**: 다음 순서로 바꾼다. 받기 → `testzip` → `.update_staging`에 풀기 → 버전·sha256을 manifest와 대조 → 모든 `.py` 문법 확인과 새 `updater.py --selftest` → 바뀔 파일을 `.rollback/v<이전>`에 복사 → `os.replace`로 하나씩 교체(재시도) → manifest에서 빠진 파일 삭제(`config.json`은 제외) → `.update_pending`. 다음 실행 때 실행기가 import로 확인하고, 실패하면 되돌린 뒤 `.update_skip`에 남긴다.
- **이유**: 하나라도 어긋나면 앱 폴더를 건드리지 않고, 바꾼 뒤 안 열리면 사용자 개입 없이 이전 버전으로 돌아온다.
- **버린 대안**: 그대로 덮어쓰기 — 중간 실패 시 복구 불가 / `.bat`에 '이전 버전으로' 메뉴 — 사용자가 판단해야 함.
- **영향/제약**: `updater.py`는 표준 라이브러리만 쓰고 새 Python 전용 문법을 피한다 (`ARCHITECTURE.md` 7절). 고치면 `tests.test_update`와 `--selftest`가 필수다. v1.7.1 이하 PC는 이 기능이 든 버전으로 한 번은 예전 방식으로 올라온다.

## D-009 | 2026-10-06 | YouTube 봇 확인을 사용자 로그인 정보로 자동 우회하지 않음
- **상태**: 채택
- **맥락**: YouTube가 "not a bot"·403·"Sign in" 오류로 다운로드를 막는 일이 잦다. 브라우저 쿠키를 쓰면 대부분 풀린다.
- **결정**: 자동으로 하는 것은 다운로드 엔진 최신화 뒤 한 번 다시 시도하는 것까지다. 크롬 로그인 정보(쿠키)는 사용자가 '크롬 로그인 정보로 받기'를 직접 켰을 때만, 이 PC 안에서만 쓴다.
- **이유**: 계정 정보를 쓰는 판단은 사용자 몫이다. 사용자 모르게 계정을 쓰면 계정 보안·이용 약관 위험을 사용자가 지게 된다.
- **버린 대안**: 막히면 자동으로 브라우저 쿠키를 써서 다시 받기.
- **영향/제약**: 계속 막히면 `core.BLOCKED_MSG`로 쿠키 옵션을 안내한다. 그래도 안 되면 YouTube Studio 직접 다운로드·Google 테이크아웃을 안내한다 (README).

## D-008 | 2026-10-06 | 다운로드 엔진(yt-dlp) 자동 관리 + Deno 자동 설치
