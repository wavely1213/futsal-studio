# DEVELOPMENT_RULES.md — 개발 규칙

> **목적**: 1인 개발 + AI 협업 환경에서 모든 코드 작업에 공통 적용되는 프로세스 규칙.
> 모든 작업의 공통 전제이므로 AI는 이 문서를 기본으로 숙지한다.

---

## 1. 작업 단위

- 하나의 작업 = 하나의 명확한 목적. "로그인 버그 수정 + 김에 리팩토링"처럼 목적을 섞지 않는다.
- 큰 기능은 독립적으로 검증 가능한 작은 단위로 쪼개서 순서대로 진행한다. (예: 배치 2 — NG 테이크·낱말 자막·스타일 점수·컷 리듬·썸네일 성능은 기능 하나씩)
- 각 단위는 완료 시점에 단위 테스트가 통과하는 상태여야 한다 (중간 상태로 방치 금지). `main` 은 언제든 `release.sh` 로 그대로 배포될 수 있다.

## 2. 브랜치 전략 (1인 개발 기준)

- 기본: `main` 브랜치는 항상 배포 가능한 상태를 유지한다. 지금까지는 `main` 하나로 작업해 왔다 (원격: `github.com/wavely1213/futsal-studio`).
- `main` 에 커밋을 푸시해도 사용자 PC 에는 바로 가지 않는다 — 사용자 PC 는 `main` 의 `manifest.json` 만 보고, zip 은 배포 커밋에 고정돼 있다. **`manifest.json` 이 바뀐 푸시 = 배포**다 (8번).
- 규모가 있는 기능/실험은 `feat/<이름>`, 버그 수정은 `fix/<이름>` 브랜치에서 작업 후 main에 병합해도 된다 (선택).
- 사소한 수정(오타, 문서, 한 줄 수정)은 main 직접 커밋 허용.
- **AI는 브랜치 삭제·force push·히스토리 재작성을 임의로 하지 않는다** (승인 필요).

## 3. 커밋 규칙

- 형식(기존 히스토리 관례): `<영역>: <요약>` 또는 `<요약>` — 예) `썸네일: 효과 그림 2단계 캐시`, `편집실 검수 87건 반영, …`. 버전 묶음은 `v1.7.1: <요약>`. `feat:`/`fix:` 같은 타입 접두는 쓰지 않는다.
- 요약은 **한국어**로 쓴다. 변경이 여러 가지면 본문에 `- ` 목록으로.
- `release.sh` 가 만드는 커밋(`release vX.Y.Z: <설명>`, `manifest vX.Y.Z`)은 손으로 만들지 않는다.
- 하나의 커밋에는 하나의 논리적 변경만 담는다. 관련 없는 파일을 함께 커밋하지 않는다.
- **커밋한 파일은 사용자 PC 로 배포된다** (`tests/`·`manifest.json` 빼고 전부 지문 목록에 들어감). 임시 파일·시험 영상·스크린샷·큰 바이너리를 커밋하지 않는다.
- **AI는 사용자가 커밋을 요청했을 때만 커밋한다.** 임의로 커밋/푸시하지 않는다.
- 커밋 전 확인: 단위 테스트 통과, 시크릿 미포함, 임시 디버그 출력(`print`·`console.log`) 제거. (`log()` 로 남기는 사용자용 기록은 디버그 출력이 아니다)

## 4. 작업 범위 (스코프) 규칙

1. 지시받은 작업 범위의 파일만 수정한다.
2. 범위 밖에서 버그·개선점을 발견하면: 수정하지 말고 `KNOWN_ISSUES.md`에 기록 + 작업 완료 보고 시 한 줄 언급.
3. 지시 작업 수행에 **필수적인** 범위 밖 수정(예: 시그니처 변경으로 호출부 수정 필요)은 허용하되, 보고에 명시한다.
4. 포매터가 자동으로 바꾸는 무관한 diff는 만들지 않는다 (수정한 부분만 포맷). `editor.html`(3천 줄)·`editor.py`(2천 줄)처럼 큰 파일일수록 주의.
5. **`thumb.html` 은 빌드 결과물이다.** 저장소 밖 원본을 고치고 다시 빌드한다. 원본을 못 찾을 때 포함 규칙은 `ARCHITECTURE.md` 7절 6번, 빌드 명령은 `AGENTS.md` 5번.
6. 같은 계산이 `editor.html`(미리보기)과 `editor.py`(내보내기)에 짝으로 있다 (`editor.py 와 같은 규칙` 주석). 한쪽을 고치면 다른 쪽도 함께 고친다 — 이것은 범위 밖 수정이 아니라 필수 수정이다.

## 5. 완료 기준 (Definition of Done)

작업은 아래를 모두 만족해야 "완료"다:

- [ ] 요구된 기능이 동작한다 (직접 실행/테스트로 확인 — 앱은 `FUTSAL_PORT=<포트> python3 app.py --browser` 로 전용 창 대신 브라우저용 서버로 띄울 수 있다. 작업 폴더는 그 앱 폴더 `config.json` 의 `workspace`)
- [ ] 기존 테스트 전체 통과 — `python3 -m unittest discover -s tests`
- [ ] 화면(`editor.*`·`thumb.*`·`style.py`·`ui.html`)을 바꿨으면 해당 e2e 묶음 통과 (`TESTING_GUIDELINES.md` 1번)
- [ ] 신규 로직에 대한 테스트 존재 (`TESTING_GUIDELINES.md` 기준)
- [ ] 린트 통과 — 설정 파일은 없다. 고친 `.py` 가 `pyflakes` 새 경고(안 쓰는 import·정의 안 된 이름)를 만들지 않고, 고친 HTML 의 JS 가 문법 오류 없이 읽힌다 (`CODING_STANDARDS.md` 3번)
- [ ] 영향받는 문서 갱신 (`DOCUMENTATION_POLICY.md` 기준 — 사용자에게 보이는 기능·화면이면 `README.md` 의 해당 절도)
- [ ] 중요 결정이 있었다면 `DECISION_LOG.md` 기록

검증을 실행할 수 없는 환경이면 "미검증"임을 완료 보고에 반드시 명시한다.
특히 **사용자는 Windows 만 쓰는데 개발·테스트는 Linux 에서 한다.** 파일 잠금·창(pywebview/WebView2)·작업 표시줄·하드웨어 인코더·Deno 설치·WebView2 글꼴처럼 Windows 실기에서만 확인되는 동작은 테스트가 통과해도 "Windows 미검증"으로 보고하고 `KNOWN_ISSUES.md` 에 남긴다 (지금 남은 항목: I-009·I-011·I-013·I-014·I-015·I-017·I-027·I-029·I-031·I-032·I-033·I-034·I-036·I-048·I-071·I-160).

## 6. 금지 사항 (승인 없이 하면 안 되는 것)

- 파일·디렉터리·브랜치·데이터 삭제
- **배포**: `release.sh` 실행, `manifest.json`·`version.txt` 를 고쳐서 푸시하는 것 (8번)
- 사용자 작업 폴더의 저장 형식 변경(프로젝트 `projects/*.json`, 스타일 `styles/*.json`, 썸네일 디자인, `*_올리기.json` 등) — 바꿔야 하면 예전 파일을 읽어 바꾸는 변환(`editor.migrate_project` 처럼)을 함께 넣고 승인받는다
- 사용자 PC 의 `config.json`·`.venv`·작업 폴더를 지우거나 덮어쓰는 코드 (업데이트는 이것들을 절대 건드리지 않는다)
- 외부로 데이터를 전송하는 신규 연동 (지금 앱이 밖으로 나가는 곳은 `PROJECT_CONTEXT.md` 6절 표가 전부다 — 유료 AI API 는 없다)
- YouTube 봇 확인을 사용자 계정 정보로 **자동** 우회하는 코드 (쿠키는 사용자가 브라우저를 직접 고를 때만)
- 시크릿 파일 수정 (지금은 시크릿이 없다 — 생기면 `SECURITY_GUIDELINES.md`)
- `requirements.txt` 변경 — 바뀐 버전이 나가면 모든 사용자 PC 에서 pip 설치가 돈다 (`DEPENDENCY_POLICY.md`)
- 히스토리 변경 (force push, rebase, reset --hard)

## 7. 보고 규칙

- 결과 중심으로 간결하게: 무엇을 바꿨는지, 검증 결과, 남은 것/가정 순.
- 과정 나열·자화자찬·불필요한 요약 반복은 하지 않는다.
- 문제가 생겼으면 시도한 것, 실패 원인, 선택지를 짧게 제시하고 판단은 소유자에게 넘긴다.
- Windows 실기에서 확인하지 못한 항목은 따로 한 줄로 적는다.

## 8. 배포 규칙 (`release.sh`)

> 배포 절차의 기준 문서는 이 절이다. 사용자 PC 쪽 설치·되돌리기는 `ARCHITECTURE.md` 6절 '업데이트 흐름'.

- 명령: `./release.sh X.Y.Z "변경 내용 한 줄"` (커밋 메시지 끝에 붙일 줄은 `RELEASE_TRAILER` 환경 변수). 소유자 승인 후에만.
- 배포 전: 단위 테스트 전체 + 영향받는 e2e 묶음이 통과한 상태여야 한다. `release.sh` 자체는 `tests.test_update` 만 돌리고, 실패하면 아무것도 커밋하지 않고 멈춘다.
- **`release.sh` 는 `git add -A` 를 한다.** 작업 트리에 커밋하지 않은 다른 작업이 있으면 그것까지 배포된다 → 그럴 때는 깨끗한 클론에서 배포한다.
- 하는 일: `version.txt` 올림 → `git add -A` → 파일마다 sha256 을 적은 `manifest.json`(`tests/`·`manifest.json`·링크 제외) 과 함께 **배포 커밋** `release vX.Y.Z: <설명>` → zip 주소(`https://github.com/wavely1213/futsal-studio/archive/<배포 커밋>.zip`)와 `commit` 을 더한 **두 번째 커밋** `manifest vX.Y.Z` → `main` 푸시. 태그 `vX.Y.Z` 푸시는 403 으로 실패하지만 업데이트와 무관하다 (D-011, `KNOWN_ISSUES.md` I-010).
- 모든 `.py` 는 설치 전에 사용자 PC 의 Python 으로 문법 확인을 받고, 새 `updater.py` 는 `--selftest` 를 통과해야 설치된다. `updater.py` 는 표준 라이브러리만 쓰고, 최신 Python 에서만 되는 문법(예: 3.12 의 따옴표 겹친 f-string)은 어떤 `.py` 에도 쓰지 않는다.
- v1.7.1 이하 PC 는 예전 방식(zip 받아 덮어쓰기 + pip)으로 받는다 — 배포 커밋 안의 `manifest.json` 에도 파일 목록이 있어야 하므로 `release.sh` 를 거치지 않는 수동 배포는 하지 않는다.
- 배포 뒤: 이전 버전 → 새 버전 업데이트가 실제로 되는지 확인하고 결과를 보고한다.
