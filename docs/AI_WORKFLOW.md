# AI_WORKFLOW.md — AI 작업 절차

> **목적**: AI가 작업 지시를 받았을 때 따르는 표준 절차와 행동 원칙.
> `AGENTS.md` 0번(협업 원칙)이 철학이라면, 이 문서는 그 실행 매뉴얼이다.

---

## 1. 행동 원칙 (우선순위 순)

1. **지시받은 작업 완수가 최우선.** 소유자가 말한 것을 먼저, 말한 범위대로 처리한다.
2. **판단은 소유자, 실행은 AI.** 타당성·방향성·윤리성·리스크 감수 여부는 소유자가 결정한다. AI는 결정에 필요한 정보를 간결하게 제공할 뿐, 결정을 가로막지 않는다.
3. **우려는 1회, 한두 문장.** 리스크가 보이면 작업 시작 시 짧게 언급하고 진행한다. 소유자가 "진행해"라고 하면 반복하지 않는다.
4. **거절 대신 시도.** "권장하지 않는다", "복잡하다"는 이유로 작업을 축소·변형하지 않는다. 요청 그대로 시도하고, 정말 불가능할 때만 이유 + 최근접 대안을 보고한다.
5. **질문 최소화.** 사소한 결정(이름, 파일 위치, 세부 구현)은 프로젝트 관례에 맞는 기본값으로 진행하고 가정을 보고에 명시한다. 질문은 (a) 파괴적 작업, (b) 해석에 따라 공수가 크게 갈리는 경우에만.

## 2. 표준 작업 절차

### ① 이해 (Understand)
- 지시를 읽고 **무엇이 완료 조건인지** 파악한다.
- 관련 문서 확인: `AGENTS.md` 문서 맵에서 해당 작업 유형의 문서만.
- 관련 코드 확인: 수정 대상 + 그 주변(호출부, 유사 패턴)을 먼저 읽는다. **읽지 않고 쓰지 않는다.**
- 이 프로젝트에서 같이 읽어야 하는 것은 다음과 같다.
  - **짝 파일**: 화면과 서버는 짝이다. `editor.html` ↔ `editor.py`, `thumb.html`(원본) ↔ `thumb.py`, `ui.html` ↔ `app.py` 경로.
  - **`thumb.html` 원본**: `thumb.html`은 빌드 산출물이고 원본은 저장소 밖에 있다(`ARCHITECTURE.md` 7절 6번).
  - **배포 경로 문서**: `updater.py`·`release.sh`·`config.json`을 건드리면 먼저 `ARCHITECTURE.md` 7절을 읽는다.
- `git status`로 작업 트리를 확인한다. 내가 만들지 않은 변경은 다른 작업이 진행 중일 수 있으니 건드리지 않는다.

### ② 계획 (Plan)
- 3단계 이상 작업은 할 일 목록을 만들어 제시하고 진행한다.
- 해석이 필요한 지점은 채택한 해석을 명시한다.
- 단순 작업(한두 파일 수정)은 계획 생략하고 바로 진행.

### ③ 구현 (Implement)
- 작은 단위로 구현하고 단위마다 동작 확인.
- 스코프 준수 (`DEVELOPMENT_RULES.md` 4번), 코딩 표준 준수 (`CODING_STANDARDS.md`).
- 이 프로젝트에서 지킬 것은 다음과 같다.
  - **사용자 데이터 보존**: 편집본·썸네일 디자인·`config.json`을 덮어쓰지 않는다. 다시 만든 결과는 옆에 추가하고, 바꾸기 전에 백업한다(`ARCHITECTURE.md` 7절 8번, `DOMAIN_KNOWLEDGE.md`).
  - **화면 문구**: 비개발자용 쉬운 해요체로 쓴다. 예외 메시지가 곧 화면 문구다(`CODING_STANDARDS.md` 5번).
- 막히면 같은 시도를 3회 이상 반복하지 말고, 시도 내역 + 원인 분석 + 선택지를 보고한다.

### ④ 검증 (Verify)
- 테스트·린트·빌드 실행 (`TESTING_GUIDELINES.md`, 명령은 `AGENTS.md` 5번). 통과 확인 후에만 완료 선언. 최소한 다음을 확인한다.
  - 단위 전체(`python3 -m unittest discover -s tests`)
  - 고친 화면의 e2e 묶음(편집실 `ed2_test.py`, 썸네일 `th2_test.py`, 스타일 배우기 `style_test.py`)
  - 고친 `.py`의 문법·pyflakes, 고친 HTML의 JS 문법
  - `updater.py`를 고쳤다면 `python3 updater.py --selftest`
- 화면을 고쳤으면 앱을 띄워(`python3 app.py --browser`, 필요하면 `FUTSAL_PORT`) 실제로 열어 본다. 저장소의 `config.json`은 바꾸지 않는다.
- 보안 관련 작업이면 `SECURITY_GUIDELINES.md` 6번 체크리스트 확인.
- 실행 불가 환경이면 "미검증" 명시.
  - 개발 PC는 Linux다. Windows에서만 드러나는 동작은 테스트가 통과해도 **"Windows 미검증"**으로 보고한다 (대상 동작은 `DEVELOPMENT_RULES.md` 5번).

### ⑤ 기록 (Record)
- `DOCUMENTATION_POLICY.md` 2번 표에 따라 영향받은 문서 갱신.
- 스코프 밖 발견 사항은 `KNOWN_ISSUES.md`에, 중요 결정은 `DECISION_LOG.md`에.
- 사용자에게 보이는 기능이 바뀌었으면 `README.md` 사용자 안내도 고친다.

## 3. 결과 보고 형식

간결하게, 이 순서로:

```
변경: 무엇을 어떻게 바꿨는지 (1~3줄)
검증: 실행한 검증과 결과 (단위 N개 통과, e2e 묶음 M/K 확인 등 · Windows 미검증 항목)
가정/남은 것: 채택한 해석, 미검증 항목, 발견한 이슈 (없으면 생략)
```

과정 중계, 자기 평가, 동일 내용 반복은 하지 않는다.

## 4. 세션 시작 체크리스트 (새 대화마다)

1. `AGENTS.md` 읽기 (이 프로젝트의 규칙 파악)
2. 지시 유형에 맞는 `docs/` 문서 확인
3. `KNOWN_ISSUES.md` 훑기 (지시 작업과 겹치는 이슈가 있는지)
4. `git status`·`git log --oneline -5`로 작업 트리와 최근 배포(`release v…`·`manifest v…` 커밋)를 확인한다.
5. 작업 시작

## 5. 하지 않는 것

- 지시 없는 커밋·푸시·배포
  - 특히 `./release.sh`는 `main`에 푸시하는 순간 모든 사용자 PC의 업데이트가 된다. 소유자 승인 없이 실행하지 않는다.
  - `release.sh`는 `git add -A`를 하므로, 다른 작업이 섞인 작업 트리에서 실행하지 않는다.
- 지시 없는 대규모 리팩토링·파일 이동·의존성 추가
- 저장소의 `thumb.html`만 직접 고치기 (원본을 고쳐 다시 빌드한다)
- 저장소 `config.json`을 개발·테스트용 값으로 바꾸기
- 완료되지 않은 것을 완료로 보고
- 같은 우려·경고의 반복
- 소유자의 결정을 재차 설득하려는 시도
